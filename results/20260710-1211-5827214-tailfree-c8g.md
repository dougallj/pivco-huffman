# tail-free NEON decode — Graviton 4 (c8g.large) A/B vs main (2026-07-10)

Branch `tail-free` @ 5827214 vs `main` @ 695c36e.  EC2 spot c8g.large
(Graviton 4, Ubuntu 24.04, gcc 13.3), `taskset -c 1`, two interleaved
`pivco_huffman_bench 20 --all` pairs, best-of-2 per side.  A/A spread
main1 vs main2 was within ~0.5 % on nearly every row — much cleaner
than the Mac hosts.  Raw captures:
`c8g-20260710-1211-{tailfree-5827214,mainbase-695c36e}.txt`.

## Decode (pivco_bu, M/s, best-of-2)

**geomean +1.8 %, min −5.5 %, max +9.4 %** over 30 distributions.

Gains: two_sym_eq +9.4 % (merge_cst_cst single-loop), source_c +4.6 %,
log_apache/proba02 +4.4 %, bell_s30 +3.6 %, html_wiki +3.4 %,
proba14/chinese_text +3.1 %, most other merge-heavy dists +1.5–3 %.

Regressions (both consistent across runs, so real on this host/compiler):

* **sparse_16 −5.5 %** (22.9 → 21.7 GB/s).  D=4 flat root with
  32768-sym blocks — n ≡ 0 (mod 32), so the 32-wide main loop covers
  every code and the new tail loop executes ZERO iterations; the
  algorithmic work is identical to main.  This is gcc-13 codegen /
  code-layout fallout from deleting the tail ladders (loop alignment,
  ICache placement), not the tail-free scheme itself.  M4 shows +0.4 %
  on the same row.  If it matters, re-check under gcc-15/clang and/or
  align the d4 main loop.
* flat_M7 −1.3 %: the new one-load-per-16-codes d7 kernel is slightly
  slower on Neoverse V2 than the old two-load version (M4: +1.5 %).
